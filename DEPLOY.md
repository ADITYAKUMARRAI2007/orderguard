# Deploying OrderGuard (Render + Vercel)

A live, public deployment of exactly what's in this repo — test-mode
Razorpay, single-tenant, SQLite on one machine, same honest scope as
[LIMITATIONS.md](LIMITATIONS.md). Not a production hardening pass; see that
file for what this deliberately does not claim.

**Three** services, not two: the FastAPI backend, the React frontend, and
`orderguard-freshcart` — the demo merchant (`demo_store/app.py`) that the
backend's FreshCart adapter reaches over the network, not as a library
import. Skipping the third one is the mistake the first real deployment of
this project actually made: every search/checkout failed with a 500 that
Chrome reported as a CORS error, because `FRESHCART_URL` had nothing
reachable to point at. See [`FAILURE_LOG.md`](FAILURE_LOG.md) F-034 for the
full diagnosis before repeating it. **I cannot create these for you** —
creating an account/service and entering real Razorpay/Anthropic/LLM keys
has to happen in your own browser, in each platform's own dashboard, so
those secrets never pass through this chat or get written into the repo.

## 1. FreshCart — the demo merchant (deploy this first)

1. In Render: **New +** → **Web Service** → this repo.
2. **Build Command**: `pip install uv && uv sync --locked`
3. **Start Command**: `uv run uvicorn demo_store.app:app --host 0.0.0.0 --port $PORT`
4. No env vars or secrets — this service holds none.
5. Deploy. Confirm it's alive:
   ```bash
   curl https://orderguard-freshcart.onrender.com/api/health
   ```
   Note the URL — the backend needs it in step 2.

## 2. Persistence — a free Postgres database (do this before the backend)

Render's free compute plan does not support persistent disks at all — not
a small one, not for a fee, not at all (confirmed by trying to attach one
via the dashboard). Without a real database, every redeploy of the backend
wipes every SQLite file under `data/`, including connector OAuth tokens
someone just connected and the Ed25519 signing key — a real incident, not
a hypothetical one (see [`FAILURE_LOG.md`](FAILURE_LOG.md) F-035). Checked
the obvious "deploy the backend somewhere else instead" alternatives —
Fly.io, Railway, Koyeb — none of them offer free persistent volume storage
either, as of this build. A free hosted Postgres is the option that costs
nothing and doesn't trade away durability.

1. Create a free project at [neon.tech](https://neon.tech) (or Supabase,
   or any Postgres host — anything SQLAlchemy/psycopg can reach works, this
   isn't Neon-specific). No CLI needed if you'd rather click through their
   dashboard; `npx neonctl auth && npx neonctl projects create` also works
   if you want it from a terminal.
2. Copy the connection string it gives you — looks like
   `postgresql://user:password@host/dbname?sslmode=require`. This is a
   real credential. Keep it out of chat, screenshots, and the repo.
3. You'll set it as the backend's `DATABASE_URL` in the next step.

## 3. Backend

1. Push this repo to GitHub (already done).
2. In Render: **New +** → **Blueprint** → connect this repo. Render reads
   [`render.yaml`](render.yaml) at the repo root and proposes services
   including `orderguard-backend`.
3. Render will prompt you to fill in every `sync: false` env var from
   `render.yaml` — **your real values, typed directly into Render's form,
   never shared with me**:
   - `DATABASE_URL` — the connection string from step 2. Every table this
     app owns (`src/orderguard/db.py`) moves here instead of a local
     SQLite file when this is set. Leave it unset only for a throwaway
     deploy you don't mind resetting on every push.
   - `FRESHCART_URL` — the URL from step 1, no trailing slash.
   - `RZP_KEY_ID`, `RZP_KEY_SECRET` — Razorpay **test-mode** keys
     (dashboard.razorpay.com → Test Mode → API Keys).
   - `RZP_WEBHOOK_SECRET` — optional; without it the webhook endpoint
     fails closed rather than accepting an unverifiable delivery.
   - `LLM_API_KEY` — a Groq key (console.groq.com/keys) is the default and
     what's actually been proven working in this repo's own live
     deployment; a fresh Gemini free-tier key was found, live, to be
     denied access to every callable model, for reasons never diagnosed
     (`FAILURE_LOG.md` F-004). Switch `LLM_PROVIDER`/`LLM_MODEL` to
     `gemini`/your own model if you'd rather use that instead — both are
     fully supported.
   - `SEARCH_API_KEY` — optional (serper.dev); web search is simply absent
     without it.
   - `ANTHROPIC_API_KEY` — needed since `render.yaml` sets
     `AGENT_RUNTIME=api`. If you already have a Claude subscription and no
     separate API key, set `AGENT_RUNTIME=subscription` instead and
     provide `CLAUDE_CODE_OAUTH_TOKEN` (generated by `claude setup-token`
     in your own terminal — this project never automates that step).
     Check `GET /api/runtime/status` on the deployed backend afterward to
     confirm which credential it actually picked up — `active_agent_
     runtime` must match the one you actually configured, or Mission halts
     with "agent runtime not configured" even though a working credential
     is sitting in the other, unused variable.
   - `CONNECTOR_TOKEN_KEY` — generate once with:
     ```bash
     python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
     ```
   - `ALLOWED_ORIGIN` — leave blank for now; step 4 below.
4. Deploy. Confirm it's alive:
   ```bash
   curl https://orderguard-backend.onrender.com/api/runtime/status
   ```

## 4. Frontend

Two options — same code, pick one or both:

**Render static site:**
1. In Render: **New +** → **Static Site** → same repo.
2. **Root Directory**: `frontend`
3. **Build Command**: `npm ci && npm run build`
4. **Publish Directory**: `dist`
5. Add `VITE_API_BASE_URL` = the backend URL from step 2 (no trailing
   slash) **before the first build** — Vite bakes it in at build time; a
   later change needs a **Manual Deploy** to take effect.
6. Deploy.

   **Known gap**: Render's static-site product has no API-configurable SPA
   rewrite rule, so a hard refresh or direct link to any route other than
   `/` returns a 404 (the file genuinely doesn't exist; only `/index.html`
   does). Fix it manually: the deployed static site → **Redirects/Rewrites**
   → add `/*` → `/index.html`, type **Rewrite**. No blueprint field or API
   call sets this today.

**Vercel** (recommended — the SPA rewrite above is automatic, no manual
step, via [`frontend/vercel.json`](frontend/vercel.json)):
```bash
cd frontend
vercel login   # your own browser OAuth, not automatable from here
vercel --prod --build-env VITE_API_BASE_URL=https://orderguard-backend.onrender.com
```

## 5. Wire the frontend(s) to the backend

The backend's CORS accepts a **comma-separated list** in `ALLOWED_ORIGIN`
(see `src/orderguard/app.py`) specifically so it can serve more than one
deployed frontend at once — without it set at all, it defaults to
allowing everything, fine for testing but worth tightening for real use:

1. Backend service → **Environment** → set `ALLOWED_ORIGIN` to your
   frontend URL(s), comma-separated if more than one, no trailing slash —
   e.g. `https://orderguard-frontend.onrender.com,https://your-app.vercel.app`.
2. Save — this restarts the backend (no rebuild needed, it's read at
   startup from `os.environ`).

## 6. Verify

Open a frontend URL. Run a real order through Shop end to end and confirm
the Razorpay Checkout modal opens against your test-mode key — the same
flow already proven locally throughout this project's development, now
proven again against the deployed FreshCart service from step 1. The
Connectors page's "Connected via your Claude account" panel will show
whatever `claude mcp list` reports were it to run on the backend's own
machine, which is nothing (no Claude Code CLI runs there) — that panel is
honestly a local-machine-only feature, not a deployment bug.

## What this deployment does not attempt

Real auth, multi-tenancy, high availability, or real (non-test-mode)
payments — see [LIMITATIONS.md](LIMITATIONS.md). Free-tier Render web
services and Neon's free-tier Postgres both spin down after inactivity and
take a few seconds to wake on the next request; worth knowing before a
live judge demo, not something this repo's code controls.
